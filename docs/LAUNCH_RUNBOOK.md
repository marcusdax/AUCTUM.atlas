# Launch runbook — RoofPro CRM

Operational guide for running, verifying, backing up and rolling back the stack.
Assumes the repo root `F:\Atlas Helios\atlas-helios-platform` (adjust paths elsewhere).

---

## 1. Prerequisites

| Component | Requirement |
|---|---|
| Docker | Docker Desktop / Engine 24+ with Compose v2 |
| PowerShell | 7.0+ (`pwsh`) for `scripts/*.ps1` |
| Node.js | 20+ — only for host-side dev commands (`npm test`, `npm run seed:demo`) |
| Ports | 3000 (web), 5000 (API), 5432 (Postgres), 6379 (Redis) |
| Credentials | `backend/.env` (created by the launcher) |

## 2. First launch

```powershell
pwsh -File scripts\launch.ps1          # generates .env, builds, starts, waits, seeds demo
# or: START.bat
```

Expected: `docker compose ps` shows `roofpro-postgres`, `roofpro-redis` healthy,
`roofpro-backend` healthy, `roofpro-frontend` healthy. Then:
http://localhost:3000 → sign in `demo@roofprocrm.com` / `RoofPro!2026`.

Flags: `-Rebuild` forces a rebuild; `-NoSeed` skips demo data; `-NoOpen` skips opening the browser.

## 3. Verification (post-change or post-deploy)

```powershell
npm run smoke                                   # 20+ checks; exits non-zero on failure
docker compose ps                               # all healthy
curl http://localhost:5000/api/v1/health
curl http://localhost:5000/api/v1/ai/status
```

Smoke report JSON is written to `runs/smoke-<timestamp>.json`. A healthy run looks like:
health, web, auth, leads, jobs, calendar, NOAA storms (or SKIP if NOAA unreachable), storm-intel
overview/sync/geojson/impact/rescore, AI status/storm-brief/map-copilot/lead-insights/usage/providers.

Manual UI checks after a deploy:
1. Sign in → Dashboard Quick Start renders, onboarding tour opens once (replay from header).
2. Leads → open a lead → storm impact score appears.
3. Storm Intelligence page → Active Storms list, map, **Generate storm brief**, copilot query
   `show extreme tornado warnings` highlights the expected map area.
4. Settings → AI Gateway → providers load; add a fake key → masked row created; delete removes it.
5. DevTools → Application → Manifest present; offline toggle shows the offline banner; SW is
   registered only in production builds.

## 4. Configuration & secrets

- `backend/.env` is the single source for API runtime config (compose loads it via `env_file`).
- `JWT_SECRET`, `JWT_REFRESH_SECRET`, `AI_ENCRYPTION_KEY` are generated by the launcher.
  **Rotating `AI_ENCRYPTION_KEY` invalidates stored provider keys** — re-add them afterwards.
- `AI_BOOTSTRAP_KEYS` is optional; DB-configured providers (Settings → AI Gateway) take precedence.
- Add provider keys in the UI, not in git. Never commit `.env`.
- Compose overrides `DATABASE_URL`/`REDIS_URL` to container hostnames; do not point them at localhost
  inside compose.

## 5. Routine operations

| Task | Command |
|---|---|
| Logs (all) | `npm run stack:logs` |
| Logs (API only) | `docker compose logs -f --tail=200 backend` |
| Restart API | `docker compose restart backend` |
| Rebuild after code change | `docker compose up -d --build backend frontend` |
| Re-seed demo | `npm run seed:demo` (host) or `docker compose run --rm seed` |
| Apply Prisma schema change | `cd backend; npx prisma migrate dev` (then rebuild) |
| Database shell | `docker exec -it roofpro-postgres psql -U postgres -d roofpro_crm` |
| Redis shell | `docker exec -it roofpro-redis redis-cli` |
| Stop | `npm run stop` |
| Stop + wipe data | `pwsh -File scripts\stop.ps1 -Volumes` |

Prisma: the API entrypoint runs `prisma db push --skip-generate` on boot (fine for this monolith,
acceptable for dev/staging). For production, review the diff and use versioned migrations:
`npx prisma migrate dev --name <change>` locally, commit `prisma/migrations`, and switch the
entrypoint to `prisma migrate deploy`.

## 6. Backups & restore

```powershell
# Backup database + uploads
docker exec roofpro-postgres pg_dump -U postgres -d roofpro_crm -Fc > runs\db-$(Get-Date -f yyyyMMdd-HHmm).dump
Compress-Archive -Path backend\uploads\* -DestinationPath runs\uploads-$(Get-Date -f yyyyMMdd-HHmm).zip -Force

# Restore into a clean database
docker exec -i roofpro-postgres pg_restore -U postgres -d roofpro_crm --clean --if-exists < runs\db-YYYYMMDD-HHMM.dump
```

Redis holds cache/session/refresh-token state and the socket adapter; losing it logs users out and
forces a refresh — acceptable. Postgres and uploads are the state that matters.

## 7. Monitoring & alerts (minimum viable)

- Uptime: probe `GET /api/v1/health` every minute; alert after 2 failures.
- API health detail: `GET /api/v1/ai/status` — providers, cooldowns, usage; alert if fallbackRate
  stays at 1.0 during business hours *and* AI features are expected.
- Resources: container CPU/memory + Postgres connections; scale API replicas only after moving
  Socket.IO to the Redis adapter across nodes (it already supports it) and S3 for uploads.
- Logs: JSON via Winston → collect from stdout (Docker log driver) or mount `backend/logs`.
- Errors: Sentry DSN is not wired; add `@sentry/node` before production (roadmap).

## 8. Incident runbook

| Symptom | Diagnosis | Action |
|---|---|---|
| Web 502 | API unhealthy | `docker compose ps`, `docker compose logs --tail=100 backend`; restart API; check DB creds |
| API 500 on most endpoints | DB down / schema drift | `docker exec roofpro-postgres pg_isready`; check `docker compose logs postgres`; run `npx prisma db push` after review |
| Login fails for everyone | JWT secret changed / Redis lost refresh tokens | Expect re-login; if secret rotated, all sessions invalid (documented) |
| Storm page empty | NOAA outage | Expected: cached events; check `GET /storm-intel/overview`; no action |
| AI briefs all `heuristic` | No healthy provider | Check `/ai/status`, provider test, cooldowns; add provider |
| AI 429 storms | Free-tier quota | Add/rotate provider, lower priority of the throttled one |
| Disk full | uploads/logs/volumes | Prune logs, move uploads to S3, expand volume |
| Slow queries | Missing indexes/large tables | `pg_stat_statements`, add indexes (leads/jobs/posts already indexed) |

Rollback after a bad deploy:

1. `git log --oneline` → identify the last good commit (the repo tracks launch work in commits).
2. `git switch --detach <good-commit>`
3. `docker compose up -d --build`
4. If the schema changed and data is incompatible, restore the latest dump (§6).

## 9. Security hardening checklist

- [ ] Replace JWT secrets with 48+ random chars; restart API (invalidates sessions).
- [ ] Terminate TLS at a reverse proxy / load balancer; never expose `:5000` publicly.
- [ ] Restrict Postgres/Redis ports to the internal network (remove host port mappings in prod).
- [ ] Change the demo password or delete demo users before real customer data.
- [ ] Rotate provider keys; keep `AI_ENCRYPTION_KEY` in a secret manager, not `.env`.
- [ ] Enable Postgres TLS + automated backups with PITR.
- [ ] Run `npm audit` / Dependabot; pin base images.
- [ ] Add rate limiting at the edge (the API has express-rate-limit, but edge limits protect better).
- [ ] Review uploads: MIME allow-list + size caps are enforced server-side; add AV scanning for public deploys.

## 10. Release notes process

1. Update `docs/CHANGELOG.md` (Keep-a-Changelog format) + `docs/BLUEPRINT_COVERAGE.md` statuses.
2. `npm test` (backend + frontend), `npx tsc --noEmit` both apps.
3. `docker compose build` and run `npm run smoke` against the rebuilt stack.
4. Tag: `git tag -a vX.Y.Z -m "…"`.
